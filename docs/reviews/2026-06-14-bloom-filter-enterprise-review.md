# BloomFilter 企业级修复报告

# 问题清单

1. **初始化失败会误拦截真实数据**
   - 原实现先创建空过滤器，再同步查询数据库；查询失败后空过滤器继续工作，合法 ID 会返回 `false`。
   - 风险：数据库或网络短暂故障会把正常请求长期误判为不存在。

2. **用户过滤器永远没有数据库初始化**
   - 原实现只加载商品 ID，用户过滤器始终为空。
   - 风险：一旦用户链路接入过滤器，全部存量用户都会被拦截。

3. **重建与新增并发时可能丢 ID**
   - 直接替换过滤器引用时，重建期间新增的数据可能只写入旧对象。
   - 风险：新数据在下一轮重建前被错误判定为不存在。

4. **多实例之间状态不一致**
   - JVM 本地过滤器没有新增数据广播，A 实例新增的数据无法进入 B 实例。
   - Redis Pub/Sub 又不具备消息持久化，实例离线时会漏消息。

5. **全表实体加载造成启动性能和内存风险**
   - `selectList(null)` 一次加载全部商品实体，再转换成 ID。
   - 风险：数据量增大后启动慢、堆内存尖峰、Full GC，甚至 OOM。

6. **事务一致性缺失**
   - 如果保存后立即写过滤器，而事务最终回滚，会产生数据库不存在但过滤器认为可能存在的脏状态。

7. **职责过度集中和配置硬编码**
   - 管理器同时负责数据库查询、启动初始化、内存状态和业务同步；容量、误判率不可配置。

# 修复方案设计

## 1. 初始化失败与 fail-open

- 方案 A：失败后继续使用空过滤器。实现简单，但会产生致命漏判，淘汰。
- 方案 B：失败时完全禁用过滤器。正确，但状态切换和恢复能力弱。
- 方案 C：维护 READY/NOT_READY 状态；NOT_READY 时非空合法 ID 一律放行，重建成功后原子切换。

**落地：方案 C。** 正确性优先，初始化故障只会增加数据库压力，不会误伤正常请求。

## 2. 全量加载与分页性能

- 方案 A：继续一次性读取完整实体。代码少，但内存和网络成本最高。
- 方案 B：普通 offset 分页。避免一次性加载，但深分页越来越慢。
- 方案 C：按递增主键游标分页，只查询 ID。

**落地：方案 C。** 查询复杂度稳定，每批默认 5000 条，不创建无用实体对象。

## 3. 重建覆盖并发写入

- 方案 A：全程加写锁。正确但重建时间长，会阻塞新增请求。
- 方案 B：直接构建后替换。性能好，但存在新增 ID 丢失窗口。
- 方案 C：锁外构建，使用 pending 集合记录新增 ID；短锁内合并 pending 后原子替换。

**落地：方案 C。** 重建期间读取无锁，新增只进入短临界区，同时保证不丢数据。

## 4. 多实例同步与 Pub/Sub 丢消息

- 方案 A：每次只靠定时全量重建。可靠但新数据可见延迟长、数据库压力高。
- 方案 B：只用 Redis Pub/Sub。实时，但实例离线和网络抖动会丢消息。
- 方案 C：Pub/Sub 实时同步 + 每 30 分钟数据库全量校准。
- 方案 D：RedisBloom 作为集中式过滤器。强一致性更易管理，但增加模块和运维依赖。

**落地：方案 C。** 符合当前项目依赖，Pub/Sub 提供实时性，周期重建负责最终收敛。

## 5. 事务一致性

- 方案 A：保存后直接调用管理器。简单，但事务回滚时产生脏数据。
- 方案 B：手工注册事务同步回调。可控，但业务代码侵入明显。
- 方案 C：发布领域事件，使用 `@TransactionalEventListener(AFTER_COMMIT)` 处理。

**落地：方案 C。** 只有数据库提交成功才同步，业务服务与缓存基础设施解耦。

# 最终修改代码

- `BloomFilterManager`：改为 `AtomicReference<FilterState>`、fail-open、`BloomFilter<Long>`、短锁和 pending 合并。
- `BloomFilterRebuildService`：启动后异步初始化，商品/用户独立游标分页重建，失败保留旧状态。
- `BloomFilterSyncService`：事务提交后本地更新并广播 Redis Pub/Sub，非法消息安全降级。
- `ProductMapper`、`UserMapper`：新增主键游标 ID 查询。
- `ProductServiceImpl`、`UserServiceImpl`：新增方法加入事务并发布创建事件。
- `CacheProperties`、`application.yaml`：容量、误判率、页大小、重建周期配置化。
- 新增 10 个 BloomFilter 定向测试，项目完整 566 个测试全部通过。

# 面试追问与答案

## 初始化与 fail-open

**追问 1：为什么不用 fail-close？**  
标准答案：BloomFilter 在这里是防穿透优化，不是权限或风控边界。fail-close 会把基础设施故障扩大为业务不可用；fail-open 最坏是临时增加数据库压力。  
深度追问：如何防止 fail-open 击穿数据库？答：配合空值缓存、请求合并、限流、熔断和告警。

**追问 2：BloomFilter 为什么不会漏判？**  
标准答案：已插入元素对应的多个 bit 都会被置位，只要过滤器没有被错误重建、替换或清空，查询不会返回 false。  
深度追问：为什么工程上仍会漏判？答：通常来自初始化不完整、并发替换丢写、多实例不同步，而不是算法本身。

**追问 3：READY 状态如何保证线程可见性？**  
标准答案：状态通过 `AtomicReference` 整体发布；filter 与 ready 放在同一个不可变状态对象中，避免分别更新产生中间状态。  
深度追问：只用 `volatile boolean` 是否足够？答：还需保证过滤器引用与状态有一致的发布顺序，整体原子状态更稳妥。

## 并发重建

**追问 1：为什么不锁住整个重建过程？**  
标准答案：数据库分页可能持续数秒甚至更久，长锁会阻塞新增写入。锁外构建、锁内合并和替换把临界区缩短到内存操作。  
深度追问：读取为什么不加锁？答：读取先取得不可变状态快照，Guava 位数组使用原子更新，引用替换由 `AtomicReference` 保证可见。

**追问 2：pending 集合解决了什么竞态？**  
标准答案：它记录重建快照开始后可能未包含的新增 ID，替换前合并到新过滤器，避免这些 ID 随旧过滤器一起丢失。  
深度追问：pending 会不会无限增长？答：每次成功重建后清空；持续重建失败时会增长，需要通过监控和容量告警控制。

**追问 3：为什么商品和用户使用独立锁？**  
标准答案：两类数据互不依赖，独立锁可避免商品重建或写入阻塞用户链路，降低锁竞争和故障影响范围。

## Redis 与多实例

**追问 1：Redis Pub/Sub 为什么会丢消息？**  
标准答案：它不持久化消息，也没有消费确认；订阅者断线或处理异常期间的消息不会补发。  
深度追问：要求可靠投递应使用什么？答：Redis Streams、RocketMQ 或 Kafka，并结合消费确认、重试和幂等。

**追问 2：为什么这里仍选择 Pub/Sub？**  
标准答案：BloomFilter 是可重建的派生数据，消息天然幂等，短暂遗漏可以由定时全量校准修复，成本低且实时性足够。

**追问 3：所有实例同时全量重建会怎样？**  
标准答案：可能形成周期性数据库读峰值。生产中可增加实例级随机初始延迟、限速或由配置错峰；不能简单用全局锁只让一个实例重建，因为每个实例都有自己的本地过滤器。

## 数据库分页与性能

**追问 1：为什么游标分页优于 offset？**  
标准答案：大 offset 通常需要扫描并丢弃前面的记录；主键游标可以利用索引从上次 ID 后继续，性能更稳定。

**追问 2：重建过程中新增和删除如何处理？**  
标准答案：新增由事务事件和 pending 合并保证；删除不会造成漏判，只会留下允许访问数据库的假阳性，下一次重建自然清除。

**追问 3：容量估算错误有什么影响？**  
标准答案：实际插入量远超预计值会提高误判率，但不会直接产生漏判；应监控业务数据量并配置合理容量。

## 事务事件

**追问 1：为什么必须 AFTER_COMMIT？**  
标准答案：避免事务回滚后缓存先写成功，保证派生缓存只反映已提交数据。

**追问 2：提交成功但事件处理失败怎么办？**  
标准答案：主数据已经提交，不能回滚业务；记录错误并依靠周期重建恢复。强可靠场景应使用 Outbox Pattern。

**追问 3：Outbox 与当前方案的区别？**  
标准答案：Outbox 在同一数据库事务中落业务数据和事件记录，再由后台可靠投递，可解决提交后进程崩溃导致的事件丢失，但复杂度更高。

# 企业级评级

**评级：高级，接近企业级。**

当前实现已具备 fail-open、异步分页重建、并发写保护、事务后同步、多实例最终一致性、配置化和测试覆盖。要达到更严格的大规模企业级，还应增加 Micrometer 指标与告警、重建耗时和 pending 大小监控、错峰调度，以及在极高可靠要求下将 Pub/Sub 升级为 Outbox + 可靠消息队列。
