# CacheKeyCleaner 企业级缓存失效加固设计

## 1. 目标与范围

本设计对 `CacheKeyCleaner` 及其端到端调用链进行企业级加固，目标是解决高并发、多实例和事务场景下的缓存一致性问题，同时逐步降低 Redis `SCAN` 的使用。

本次范围包括：

- `CacheKeyCleaner` 精确删除和模式删除。
- 数据库事务提交后的缓存失效。
- 多实例 JVM L1 缓存失效同步。
- Redis 删除失败后的有限异步重试。
- 核心列表、搜索和分页缓存迁移到版本化 Key。
- 参数校验、Glob 匹配、指标、日志和测试。

本次不引入 RocketMQ、Redis Streams 或 Outbox。Redis Pub/Sub 仅用于可恢复的 L1 失效通知，L1 TTL 负责最终兜底。

## 2. 当前问题清单

### 2.1 删除顺序存在并发旧值回填

当前流程先清理 L1，再删除 Redis：

```text
线程 A 清理 L1
线程 B 从尚未删除的 Redis 读取旧值并回填 L1
线程 A 删除 Redis
最终 L1 仍保留旧值
```

风险是更新完成后，本机仍可能持续返回旧数据直到 L1 TTL 到期。

### 2.2 多实例 L1 无法同步失效

当前代码只删除调用实例的 L1。其他实例的普通 L1 和热点 L1 仍可返回旧值。

### 2.3 缓存失效与数据库事务脱节

若事务提交前删除缓存，并发请求可能读取数据库旧值并重建缓存。若事务最终回滚，则不必要地删除了有效缓存。

### 2.4 模式删除不能保证强一致

Redis `SCAN` 不是一致性快照。遍历期间新增、删除或迁移的 Key 可能导致重复或未覆盖结果。该能力不能作为核心业务强一致失效机制。

### 2.5 Redis Glob 到 Java 正则转换不完整

当前仅支持 `*`，没有正确覆盖 `?`、字符集合和否定字符集合，本地 L1 与 Redis 的匹配结果可能不一致。

### 2.6 正则存在重复编译

本地失效使用 `String.matches()`，每个 Key 都会重复编译正则，缓存数量大时产生不必要的 CPU 和对象分配。

### 2.7 缺少危险参数保护

`null`、空字符串和单独的 `*` 没有被拒绝，可能触发异常或误删整个缓存空间。

### 2.8 Redis 异常缺少明确补偿策略

当前删除失败直接抛出异常，可能出现部分缓存已失效、部分未失效的状态；也没有有限重试、失败指标和告警边界。

### 2.9 Redis Cluster 扩展风险

当前模板级 `SCAN` 适用于现有部署，但未来迁移 Redis Cluster 时不能默认一次扫描覆盖全部主节点。因此核心业务必须降低对模式扫描的依赖。

## 3. 方案对比

### 方案一：仅修补 CacheKeyCleaner

内容：

- Redis 先删、L1 后删。
- 参数校验。
- 提前编译正则。
- 删除失败有限重试。

优点：

- 改动最小。
- 能解决本机并发回填和基础健壮性问题。

缺点：

- 无法解决其他实例的 L1。
- 无法解决事务提交前失效。
- 核心业务仍依赖 `SCAN`。

结论：不足以满足端到端企业级要求。

### 方案二：事务事件 + Pub/Sub + SCAN 加固

内容：

- 事务提交后触发失效。
- Redis Pub/Sub 广播 L1 失效。
- 模式删除增加校验、批处理和指标。

优点：

- 改造成本适中。
- 覆盖事务和多实例问题。
- 兼容现有调用方。

缺点：

- 核心批量缓存仍依赖 `SCAN`。
- Pub/Sub 断线期间会丢消息。

结论：可上线，但批量失效性能和扩展性仍不理想。

### 方案三：混合失效模型（最终选择）

内容：

- 列表、搜索、分页缓存使用版本化 Key。
- 单条详情缓存使用精确删除。
- Redis Pub/Sub 同步多实例 L1。
- 事务提交后触发失效。
- `deleteByPattern()` 保留为兼容入口，但禁止危险规则，不再用于核心业务。
- Redis 删除失败采用有限异步重试。

优点：

- 核心批量失效接近 O(1)。
- 避免生产核心链路扫描 Redis。
- 保留兼容能力，迁移可分阶段完成。
- 同时覆盖事务、多实例和本机并发问题。

缺点：

- 需要改造现有批量缓存调用方。
- 旧版本 Key 在 TTL 内继续占用 Redis 内存。
- Pub/Sub 仍然不是可靠消息系统。

结论：最符合当前项目规模、依赖和上线要求。

## 4. 最终架构设计

### 4.1 精确 Key 失效

适用于商品详情、用户信息等单对象缓存。

流程：

```text
校验 Key
删除 Redis
finally 清理本机普通 L1 和热点 L1
广播 KEY 失效消息
Redis 删除失败则提交有限异步重试
```

Redis 必须先于本地 L1 删除，防止并发线程用 Redis 旧值重新回填 L1。无论 Redis 是否成功，本机 L1 都必须在 `finally` 中清理。

### 4.2 版本化 Key

适用于列表、搜索、建议词、分页和聚合结果。

示例：

```text
版本键：cache:product:search:version
数据键：cache:product:search:v42:<query>:<page>:<size>
```

数据变化后只递增版本键：

```text
INCR cache:product:search:version
```

新请求自动使用新版本，旧 Key 依靠 TTL 回收，不再执行模式扫描。

版本读取失败时使用明确降级策略：短时使用默认版本或绕过缓存，不能静默长期固定在旧版本。

### 4.3 兼容模式删除

`deleteByPattern()` 暂时保留，供尚未迁移的非核心调用方使用。

约束：

- 拒绝 `null`。
- 拒绝空字符串。
- 拒绝单独的 `*`。
- 限制 Pattern 最大长度。
- 使用预编译 `Pattern` 清理 L1。
- 支持 Redis Glob 的 `*`、`?`、字符集合和否定字符集合。
- 使用 `SCAN` 和批量删除。
- 记录扫描数量、删除数量、耗时和失败指标。
- 文档明确其为最终一致操作，不提供强一致保证。

迁移完成后可进一步将该方法限制为内部运维用途。

### 4.4 事务提交后失效

业务更新方法不直接执行缓存删除，而是发布缓存失效事件。

监听器使用：

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
```

只有数据库事务成功提交后才执行缓存失效。非事务调用需要定义显式降级入口，避免事件被静默丢弃。

### 4.5 多实例 L1 同步

失效消息字段：

- `operation`：`KEY`、`PATTERN` 或 `VERSION`。
- `target`：具体 Key、Pattern 或版本键。
- `sourceInstanceId`：来源实例。
- `eventId`：便于日志追踪和幂等观察。

本机完成失效后通过 Redis Pub/Sub 广播。其他实例只清理本地 L1，不再次删除 Redis，也不再次广播。

来源实例可以忽略自己的消息，因为本机 L1 已经清理。消息解析失败只记录受控告警，不能终止监听线程。

Pub/Sub 可能丢消息。当前 L1 TTL 较短，因此断线实例会最终恢复；这是本方案接受的最终一致性边界。

### 4.6 删除失败与异步重试

缓存是派生数据，Redis 删除失败不能回滚已经提交的业务事务。

失败处理：

- 立即清理本机 L1。
- 记录结构化错误日志和失败指标。
- 提交到 Spring 管理的有界线程池。
- 使用有限次数和退避重试。
- 达到最大次数后停止，记录最终失败指标。
- 拒绝策略不能无限阻塞业务线程。
- 应用关闭时由 Spring 正常停止线程池。

重试任务必须只重试 Redis 删除和广播，不重复执行业务数据库操作。

## 5. 组件职责

### CacheKeyCleaner

- 精确删除共享 Redis。
- 清理本机两类 L1。
- 兼容模式删除。
- 发布跨实例失效消息。
- 提交删除失败重试。

### CacheInvalidationEventListener

- 接收业务层缓存失效事件。
- 保证事务提交后调用 `CacheKeyCleaner`。

### CacheInvalidationSubscriber

- 注册 Redis Pub/Sub 监听。
- 校验并解析失效消息。
- 仅执行本地 L1 失效。

### CacheInvalidationRetryService

- 使用有界执行器执行有限重试。
- 管理重试次数、退避和失败指标。

### VersionedCacheKeyService

- 读取或初始化版本号。
- 构建版本化数据 Key。
- 原子递增版本。
- 为调用方隐藏版本 Key 细节。

## 6. 一致性边界

本方案采用最终一致性，不宣称缓存与数据库强一致：

- 数据库是唯一真相源。
- 事务提交后失效降低提交时序风险。
- Redis 先删降低本机旧值回填风险。
- Pub/Sub 降低多实例 L1 旧值窗口。
- L1 TTL 负责 Pub/Sub 丢消息后的最终恢复。
- 版本化 Key 避免核心批量缓存依赖非强一致的 `SCAN`。

对于必须强一致的数据，不应依赖缓存作为授权或最终判断依据。

## 7. 测试设计

### CacheKeyCleaner 单元测试

- 精确删除时 Redis 调用早于本地 L1 失效。
- Redis 删除异常时两个本地 L1 仍被清理。
- `null`、空字符串、`*` 和超长 Pattern 被拒绝。
- Glob 的 `*`、`?`、字符集合和否定集合与预期一致。
- Cursor 正常关闭。
- 批量删除按配置批次执行。

### 事务测试

- 事务提交后执行失效。
- 事务回滚时不执行失效。
- 非事务调用走明确的即时失效策略或被显式拒绝。

### Pub/Sub 测试

- KEY 消息只清理本地对应 Key。
- PATTERN 消息只清理本地匹配 Key。
- VERSION 消息清理本地版本读取结果或相关 L1。
- 不重复广播消费到的消息。
- 非法消息被忽略，监听器继续工作。
- 来源实例消息按设计忽略。

### 重试测试

- Redis 首次失败后按退避重试。
- 成功后停止重试。
- 达到最大次数后停止。
- 线程池饱和时不无限阻塞业务线程。

### 版本化 Key 测试

- 相同版本生成稳定 Key。
- 递增版本后生成新 Key。
- 旧版本数据不再被新请求读取。
- 版本读取异常时按设计降级。

### 回归测试

- 保留现有缓存测试。
- 运行完整 Maven 测试套件。
- 确认不再有核心业务调用 `deleteByPattern()`。

## 8. 实施顺序

1. 为失效操作补充参数校验、删除顺序和测试。
2. 增加本地失效专用接口，避免订阅者重复删除 Redis。
3. 增加 Pub/Sub 消息与订阅。
4. 增加 Spring 有界线程池和有限重试。
5. 增加事务提交后失效事件。
6. 增加版本化 Key 服务。
7. 逐个迁移列表、搜索、建议词、分页等核心调用方。
8. 收紧 `deleteByPattern()` 的使用范围。
9. 完整测试和调用点审计。

## 9. 企业级评价

当前 `CacheKeyCleaner` 的基础结构属于中级水平：具备统一入口、`SCAN`、批量删除和资源关闭意识，但缺少事务、多实例和高并发一致性设计。

按本设计完成后可达到高级、接近企业级水平。若未来要求可靠跨实例通知和可重放失效事件，应进一步升级到 Outbox + RocketMQ/Redis Streams，并增加完整的可观测性与告警体系。
