# 商家店铺管理设计方案 (方案一)

## 1. 架构与组件
- **User表**: 保持现有设计，仅通过 `role` 字段区分角色 (0:用户, 1:商家, 2:管理员)。
- **Shop表**: 新增该表。用于存储店铺信息和商家专属资质信息。
  - **关联方式**: 通过 `user_id` 与 `user` 表建立 1对1 关联。

## 2. 数据流与交互
- **商家登录/鉴权**: 
  - 当 `role=1` (商家) 的用户登录成功后，后端根据 `user_id` 查询 `shop` 表，获取 `shop_id`。
  - 将 `shop_id` 放入 JWT token 或 Redis 中。
  - 后续该商家的请求上下文中 (`UserContext`) 将直接包含 `shop_id`，无需每次查询数据库。
- **商家入驻/信息修改**: 提供专门的接口处理 `shop` 表的数据。

## 3. 错误处理
- 商家登录时，若找不到关联的 `shop` 记录，视为“未完善店铺信息”，允许登录但部分需要 `shop_id` 的接口应返回 `403` 或特定的业务错误码，提示前端跳转到完善信息页面。
- 防止普通用户调用需要商家权限及 `shop_id` 的接口。

## 4. 测试
- 单元测试验证角色转换与 `shop_id` 获取逻辑。
- 接口测试验证 `UserContext` 中 `shop_id` 的正确性。

## 5. 前端需要更改的详细信息 (Markdown源码)

```markdown
### 1. 登录与 Token 解析
* **变更点**: 商家登录成功后，后端的 Token payload 中或登录响应体中将包含 `shopId`。
* **前端操作**:
  - 在全局状态 (如 Vuex/Pinia 或 Redux) 和 `localStorage`/`sessionStorage` 中，除了保存用户信息外，如果是商家，需保存 `shopId`。
  - 示例数据结构：
    \`\`\`javascript
    const userInfo = {
      id: 1001,
      role: 2, // 前端视角的商家角色
      shopId: 5001 // 新增字段
    }
    \`\`\`

### 2. 路由守卫与页面重定向
* **变更点**: 后端会校验商家是否已完善店铺信息（即是否有 `shopId`）。
* **前端操作**:
  - 在商家后台的路由守卫中，如果检测到当前用户是商家，但全局状态中没有 `shopId`，应强制重定向到“店铺信息完善/入驻”页面。

### 3. API 请求调整
* **变更点**: 大部分商家相关的接口（如发布商品、订单管理等），后端会自动从 Token/上下文中提取 `shopId`。
* **前端操作**:
  - **一般情况**: 前端无需在请求参数中显式传递 `shopId`。
  - **特殊情况**: 若后端某些旧接口强制要求传 `shopId`，则从全局状态中取出并传递。请与后端确认具体接口规范。

### 4. 新增/修改页面
* **新增页面**: “商家入驻/店铺信息完善”页面，用于收集店铺名称、营业执照图片上传、法人信息等。
* **修改页面**: “店铺设置”页面，用于修改上述 `shop` 表对应的信息。
```
